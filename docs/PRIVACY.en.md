Pulse is a local Dynamic Island-style Mac utility. It is designed to show system status, the Applications list, clipboard history, memos and todos, capture tools, Bluetooth devices, and on-demand aggregate AI-account usage on the Mac where it is running.

## Data Pulse Reads

Pulse may read local data including:

- Pointer position and available display bounds while the island or pinned panels are visible, used only in memory to position panels on the current display; never logged, stored, or uploaded
- CPU usage
- Memory usage
- Disk capacity and disk I/O counters
- Network byte counters
- Battery status
- Thermal state
- The system's last boot time, used to calculate system runtime
- Names of running processes and their CPU and memory usage
- Local app bundle paths used to display app icons
- App names, bundle IDs, versions, and bundle paths from standard application locations, plus those apps' running state, used to show the Applications list
- The target app bundle path plus candidate paths, file sizes, and existence state for common user Library application support files, containers, preferences, caches, logs, launch agents, saved state, WebKit data, and HTTP storage when the user explicitly chooses Uninstall and Clean Up from the Applications module
- Local Bluetooth device names, types, connection state, Bluetooth addresses, and battery or charging-state fields exposed by macOS after the user grants Bluetooth access, used to show the Bluetooth device list, connect or disconnect paired devices, display readable battery levels and charging state, and show local low-battery alerts for Bluetooth devices; AirPods-style devices show left, right, and case battery levels when macOS returns those fields
- System clipboard changes and contents, including text, links, file URL/path representations, images, original pasteboard representations, sensitive or transient markers, and source-app information declared by the clipboard or inferred by Pulse, used to show Clipboard history; when files are copied, Pulse does not proactively read or store the file contents themselves
- Memos entered by the user in the Memo module, including memo text, todo completion state, pin state, creation time, and update time
- Full-screen, window, or custom selection pixels through the native macOS screenshot flow when the user explicitly triggers the Capture module; screenshots are written to the system clipboard
- Full-screen, window, or custom selection video frames through native macOS ScreenCaptureKit recording when the user explicitly starts recording from the Capture module; recordings do not include system audio or microphone audio
- When the user opens or refreshes the Codex provider in AI Usage: account plan type; the name, used percentage, duration, reset time, and reached state of each separate rate-limit bucket; credit balance or unlimited state; available reset credits; and account-level lifetime tokens, peak daily tokens, longest-turn duration, current and longest usage streaks, and daily aggregate tokens returned by the locally installed Codex CLI App Server
- While Claude Code is connected: per-session daily token totals and longest turn duration recorded by Pulse's local mod after each turn
- While Claude Code is connected or Codex alerts are connected: each session's state (running, waiting for your approval or answer, done, stopped with an error), the name of a built-in tool waiting for approval, the working folder's name, the turn duration, and the name and bundle ID of the app running the session (a terminal, an editor, or the Claude or Codex app), used to show agent alerts in the island; Pulse also notices when one of these apps quits (comparing only its bundle ID) and clears its sessions then, or after a session reports nothing for 3 hours

System metrics, processes, the Applications list, and the Bluetooth device list are used only to render the app interface. They are not uploaded or used for persistent tracking. The Applications list and running state are refreshed on demand in local memory and are not written to a persistent database. Application uninstall cleanup scans run only after the user opens the confirmation panel from the right-click menu, never in the background. Pulse shows full candidate paths for confirmation and only asks macOS to move user-selected items to the system Trash; it does not permanently delete them directly and does not upload candidate paths or file contents. After Bluetooth access is granted, the Bluetooth device list is refreshed at a low frequency in local memory while Pulse is running so the Bluetooth panel and low-battery alerts remain available; the refresh frequency increases while the Bluetooth panel is open. Pulse does not save Bluetooth addresses, device serial numbers, battery history, or charging history. The suggestion panel generates storage, power, thermal, memory pressure, and Bluetooth battery recommendations only from these local system metrics and Bluetooth battery readings; disabling the panel or dismissing an individual suggestion stores only the local preference and suggestion ID, not raw metric history. App bundle paths added by the user to Favorite Apps are saved in local preferences so Pulse can restore the Favorite Apps panel next time.

Clipboard history is enabled by default and is stored in the local Application Support directory after macOS allows clipboard reads. Pulse does not automatically prune by entry count by default and keeps history for 30 days; users can choose a 100, 500, 1000, or unlimited entry limit in Settings, choose an unlimited, 7-day, 30-day, or 90-day retention time, and clear history at any time. Items marked with `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType`, `org.nspasteboard.AutoGeneratedType`, remote clipboard/source markers, and similar markers are still recorded. These markers do not prevent storage, search, or copy; they only make the interface mask more sensitive entries by default. Direct paste from a double-clicked clipboard entry first writes that entry back to the system clipboard, then uses macOS Accessibility permission to send one paste shortcut to the currently focused target; Pulse does not read the target app's input contents, window contents, or accessibility tree. OCR is off by default; when enabled, image text recognition uses the local Vision framework, and OCR text is stored only in the local search index.

The Memo module stores only content the user enters directly. Notes and todos are saved as a JSON file in the local Application Support directory so Pulse can restore the list, filters, search, completion state, and pin state after restart. Copying a memo writes that memo text to the system clipboard; if Clipboard history is enabled, that copy follows the existing local Clipboard history rules. Pulse does not upload memo content, does not sync it to iCloud, Calendar, or Reminders, and does not create notifications for memos. When a memo is expanded, Pulse detects web addresses in it on this Mac and shows them as links; a link opens in the default app only when the user clicks it, and Pulse never visits links in advance or fetches previews.

The screenshot completion preview exposes user-triggered Save, Share, Edit, Pin, and Recognize Text actions. Save writes the current screenshot as a PNG only after the user chooses a location. Share hands the screenshot to the macOS share sheet, where the user chooses AirDrop, Mail, Messages, or another system share destination. Edit processes the current screenshot only in a local foreground floating editor, can add brush-based mosaic redaction, rectangles, circles, arrows, pen strokes, and text; the editor's Save, Share, and Pin actions also operate only on the current edited image, and completing the edit writes the edited image back to the system clipboard. It does not upload the image or automatically save another file. Pin keeps the current screenshot in a local foreground floating window until the user closes that window; it does not upload the image or write another file. Recognize Text uses only the local Vision framework; recognized text is not uploaded and does not replace the clipboard automatically. It is written to the system clipboard only if the user chooses Copy Text in the result window. When the user drags the screenshot preview to Finder, chat windows, or documents, Pulse provides PNG data for that drag and prepares a PNG file representation in the system temporary directory. Old temporary drag files are cleaned up by later drags.

The Capture module runs only when the user clicks a screenshot or recording action or triggers a screenshot or recording shortcut, and first use requires macOS Screen Recording permission. Pulse hides its island panel by default before calling the native macOS `screencapture` tool for screenshots; users can turn off Hide Pulse in the Capture panel when they want Pulse itself to appear in the image. Screenshots are written to the system clipboard, and if Clipboard history is enabled, that screenshot is stored as a local image entry under the existing Clipboard history rules. Before recording starts, full-screen and window recordings first reuse the native screenshot picker to create a temporary target-selection screenshot, read only the selected target metadata written by macOS, and delete that temporary screenshot immediately. Custom-region recording shows a local AppKit selection layer that dims unselected areas while keeping the selected region at its original brightness. After custom-region recording starts, Pulse keeps a non-interactive local region guide visible so the unrecorded area stays dimmed and the selected area keeps a blue boundary; Pulse excludes that guide window from the final recording output. Pulse then records the selected display, window, or region with native macOS ScreenCaptureKit and writes the `.mov` file with AVFoundation. When Hide Pulse is enabled, Pulse hides its island panel briefly before target selection; after recording starts, the Pulse island returns with elapsed time and a stop button, while ScreenCaptureKit excludes Pulse itself from the final recording output. The live macOS sharing indicator is controlled by the system and is not written into the final video by Pulse. Pulse hides the mouse pointer in recordings by default; users can turn off Hide Mouse when the pointer should be visible. Recordings are saved first to the system temporary directory and enter an island video preview after stopping; users can play the file locally before choosing to save, share, close, or discard it. Pulse moves the temporary `.mov` only after the user chooses a location in the save panel; closing, discarding, replacing the preview, quitting, or a failed save removes any still-unsaved temporary recording file. Pulse does not upload screenshots or recordings to the network. If permission has not been granted or was denied, Pulse requests access or opens the system privacy settings.

The Codex provider works only while the main or pinned AI Usage panel is open, or when the user explicitly refreshes it. It starts the locally installed `codex app-server --stdio` process and reads the account aggregates above through its documented `account/rateLimits/read` and `account/usage/read` methods. It refreshes at most every five minutes while either panel remains open and stops polling when both close. Pulse relies on the Codex CLI's existing sign-in and does not read `~/.codex/auth.json`, OAuth tokens, API keys, or Keychain contents. It also does not read prompts, responses, source code, tool output, or raw session JSONL. Returned snapshots stay only in Pulse's current process memory and are not written to a database, preferences, or files. If refresh fails, Pulse shows the error and keeps the last successful snapshot. Operational logs contain only the CLI path, process and protocol stages, quota/daily-bucket counts, and error categories; they do not contain credentials, account content, or actual token-usage values.

The Claude provider installs a local mod at `~/.claude/pulse-ai-usage-bridge`, storing only code and configuration, never usage. It reads subscription 5h/7d used percentages and reset times through the official Claude Code Mods API’s `session.start`, `session.attach`, and `session.measure` events, along with the local time this session last received those quotas in an API response, then starts the local Pulse bridge to forward only those fields. Pulse uses that time only in memory to keep the newest reading across sessions, so older sessions cannot override current quotas. It reads no conversation content and calls no model. For older terminal versions, connecting also wraps `statusLine` in `~/.claude/settings.json` while preserving its original command. That process decodes only the official `rate_limits.five_hour` and `rate_limits.seven_day` fields; other session metadata is neither saved nor forwarded to the main Pulse process, while the original command receives its unchanged input. Disconnecting removes Pulse’s generated mod and restores the status line; other settings are preserved. While connected, Pulse regenerates its own mod files at launch for the current version and install location, writing only when their contents change. Quotas reach Pulse through local distributed notifications and remain only in process memory. Pulse does not read Claude sign-in files, Keychain contents, raw transcripts, or personal files, or make additional requests to Anthropic or other services. Local usage events update Claude data. Values older than one hour or past their reset time are marked out of date and retained; Pulse cannot actively fetch Claude subscription limits. Polling continues while either the main or pinned panel is visible and stops when both close; local events may still update the in-memory snapshot.

While connected, Pulse's mod also uses the official Claude Code Mods API `turn.complete` event to read, after each turn, the four token counts the API reported for it (input, output, cache read, cache write) and the turn's duration. It adds them to a per-session, per-day file at `~/.claude/pulse-ai-usage-data/<date>/<session ID>.json`. The file holds only the day's total tokens and longest turn duration; it never holds prompts, replies, tool content, models, cost, or account details. Each session writes only its own file. Pulse reads these files when the AI Usage panel opens or a Claude usage notification arrives and totals them only in memory for lifetime, last 7/30 days, peak day, streaks, and longest turn. While reading, it folds days before yesterday into `days.json` in the same folder (one token total and longest turn duration per day) so daily totals since connecting are kept. Disconnecting deletes the whole folder; before deleting, Pulse checks that the folder holds only these files and otherwise changes nothing. These totals cover only Claude Code sessions on this Mac that loaded the mod, not claude.ai or other devices, and are never uploaded.

While connected, Pulse's mod also uses the official Claude Code Mods API `turn.start`, `tool.check`, `tool.call`, `turn.complete`, and `session.end` events. When a session starts a turn, needs your approval for a tool or an answer to a question, continues after you respond, finishes a turn, or ends, the mod calls the local Pulse bridge process with whitelisted fields only: the session ID, the working folder's name (never its path), the state, the name of a built-in tool waiting for approval (such as Bash; MCP and other tools stay unnamed), the turn duration, and the event time. The mod never reads prompts, replies, tool arguments, commands, file contents, or diffs. The bridge process walks up its own parent processes to the first regular app and reads that app's name and bundle ID, so the Open button can bring it to the front; when it finds none, it falls back to Claude Code's own `CLAUDE_CODE_ENTRYPOINT` (the desktop app or VS Code). These values reach Pulse through a local distributed notification and stay only in memory: they are never written to files or preferences and never uploaded. A session leaves memory when it ends, when you interrupt its turn, or 30 minutes after it finishes. Pulse uses them only for the island's alert panel, alert strip, and waiting count.

When you click Connect alerts on the Codex page of AI Usage, Pulse adds one official Codex hook that runs only Pulse itself to `~/.codex/hooks.json` for each of `UserPromptSubmit`, `PermissionRequest`, `PostToolUse`, `Stop`, `Interrupt`, and `SessionEnd`. Other hooks and settings in the file stay as they are, and Disconnect alerts removes only the entries Pulse added. Under Codex's rules these hooks run only after you trust them with `/hooks` in Codex; Pulse reads their trust state through the installed Codex CLI's official App Server `hooks/list` interface so it can remind you. When Codex runs a hook it writes the session ID, working directory, event name, tool name, and also the prompt, tool arguments, and last reply to the hook's standard input; Pulse decodes only the session ID, the working directory's folder name, the event name, and a built-in tool's name, and never decodes, stores, or forwards the rest. The hook prints nothing and always exits successfully, so it never changes Codex's approval or turn flow. From there, session states, host app detection, memory-only storage, and removal follow the same rules as Claude Code above. Pulse does not read `~/.codex/auth.json`, the Keychain, or raw session logs.

Connecting also adds Pulse's own mod directory to the Claude user setting `env.CLAUDE_CODE_PLUGIN_DIRS`. Other environment values and plugin directories are preserved; disconnecting removes only Pulse's directory entry. This is local loading configuration and contains no account credentials or usage values.

## Data Pulse Does Not Collect

Pulse does not collect, store, or transmit:

- Personal files
- Contacts, photos, calendars, or location data
- Keychain contents; if the user copies passwords, one-time codes, API keys, or other credentials to the system clipboard, the Clipboard module stores them locally as history and masks them by default in the list
- In-app behavior analytics or feature-usage telemetry
- Persistent records or uploads of Bluetooth addresses, device serial numbers, or persistent tracking identifiers
- Network uploads of memo content, todo content, or todo completion state
- Codex OAuth tokens, API keys, prompts, responses, source code, tool output, or raw session logs

## Network Usage

Pulse requests the TimeLikeSilver-hosted appcast over HTTPS to check whether a new version is available. When the user clicks Update, Pulse downloads the matching release archive and Sparkle verifies its signature before installation.

When the user opens or refreshes the Codex provider, the local Codex CLI uses its existing sign-in to request account-level aggregate usage from OpenAI. OpenAI receives the existing account identity needed for that request and ordinary network metadata that may include IP address, user agent, request time, and requested path; the local App Server also receives Pulse's client name and version. Pulse does not attach system metrics, process lists, application lists, Bluetooth data, clipboard contents, memos, screenshots, recordings, personal files, prompts, responses, source code, or tool output to this request. OpenAI's applicable privacy policy and account terms govern its service-side processing.

As with ordinary HTTPS requests, the appcast request may be processed with standard request metadata such as IP address, user agent, request time, and requested path. TimeLikeSilver may use these requests for security, operations, and aggregate update-check counts to understand Pulse runtime trends. Update checks do not attach CPU, memory, device model, system boot time, process lists, application lists, Bluetooth device lists, Bluetooth battery levels, Bluetooth charging state, clipboard contents, app bundle paths, file contents, or Sparkle system profiling data.

## Local Preferences

While the Pulse island is shown, Pulse uses macOS event monitoring to read the on-screen mouse pointer position and whether a button is pressed, only to decide whether the pointer is inside the island so the panel receives clicks and clicks outside it go to the app below. The pointer position is used for that check only and is never logged, stored, or uploaded, and no keyboard input is read. This monitoring needs no Accessibility permission and stops when the panel is dismissed.

When a pinned Resource Monitor or AI Usage panel first opens, Pulse reads the pointer’s display and its available bounds to position the panel. With display following enabled, it checks every 350 milliseconds while visible to preserve relative placement across displays. Locking the panel or closing it stops these checks. Re-enabling following also reads the panel’s current display bounds. Positions and bounds are never logged, persisted, or uploaded, do not trigger usage requests, and require no additional permissions.

Pulse may store local preferences, such as language, appearance, launch-at-login, the separate display-following toggles for AI Usage and Resource Monitor panels, Applications display mode, Favorite Apps bundle paths, the suggestion panel toggle, dismissed suggestion IDs, the Clipboard OCR setting, the Clipboard entry limit, the Clipboard retention-day limit, whether Pulse hides itself during screenshots and recordings, whether recordings hide the mouse pointer, and the shortcuts for waking Clipboard, waking Applications, the three screenshot modes, and the three recording modes, using macOS local storage. Memo content is stored in the local Application Support directory rather than user preferences. The Bluetooth device list, connection state, battery levels, and charging state are not written to local preferences. AI Usage snapshots and refresh errors are not written to preferences or any other persistent storage.
